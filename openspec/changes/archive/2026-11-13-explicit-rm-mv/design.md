# Design

## Context

`integrate` (`internal/ms/integrate.go:13`) replays a stage onto a newer tip with a three-way `MergeTrees(baseTree, tipTree, staged)`, then checks the result with `verifyIntegration`. Git's rename detection inside that merge is the only way moves are followed today. A tip deletion of a staged path is a modify/delete conflict, reported as kind `conflict`. `AddPaths` (`internal/ms/stage.go:184`) stages deletions and renames like `git add`. Edit records (`internal/ms/edits.go`) carry a path, and `After == ""` means a deletion. This change assumes `stage-holds-edits` is applied: `add --edits` reads no disk state. See proposal.md for the motivation.

## Goals / Non-Goals

**Goals:**
- A deletion or a move enters a stage only through `rm`, `mv`, or a Codex patch header.
- A stage's change lands at the path where the branch moved the file, even when the move came with heavy edits.

**Non-Goals:**
- Directory moves (`mv dir/ other/`). `mv` takes one file. Moving a directory is several `mv` calls.
- Reading `Multistage-Moved` trailers from commits outside the base..tip range.
- Moves in patches given to `apply`. A patch is an explicit action: `apply` stages its renames as before, without a trailer, and other stages follow them through Git's rename detection.

## Decisions

- **Moves live in the stage metadata.** `Meta` gets `Moves []Move` (old, new). `mv` updates the stage index (remove old, add new with the staged blob of old) and appends the move. `restore --staged` of either path drops the move. `commit` turns the moves into trailers and clears them when the commit lands. *Alternative:* infer moves from the staged D+A pairs. Rejected: that brings back the guessing the change removes.
- **Rewrite paths before the merge.** Before `MergeTrees`, `integrate` reads `git log --format=%(trailers:key=Multistage-Moved,valueonly) base..tip`, oldest first, and builds an old→new map that follows chains. It renames those entries in `baseTree` and `staged` so all three trees share the tip's paths, then merges. The trailers of one commit form one simultaneous step: each commit's map is applied to the result of the earlier commits, so `a -> c` and `c -> d` in one commit move `a` to `c`. `moveEntries` reads all old entries first, then removes them, then writes the new ones. Only entries that `baseTree` holds are moved, so a file the stage added stays where the stage put it. The rename detection of the merge still covers commits without trailers. *Alternative:* `merge-tree` rename hints. Rejected: Git has no option to supply renames.
- **`path-deleted` is detected before the merge.** For each path that the staged change modifies, after the move rewrite: if `baseTree` holds it and `tipTree` does not, the deleting commit is `git log -1 --diff-filter=D --format=%H base..tip -- <path>`. Any such path gives `path-deleted` with all the paths and commits. `--recreate <path>` removes the path from `baseTree` before the merge, so the staged version merges as an addition. If the tip has re-added the path, that addition conflicts as usual.
- **Trailer paths are quoted.** A path with `->`, `"`, `\`, a control character, or leading or trailing whitespace is written as a C-style quoted string, as `git diff` writes paths, and the reader unquotes it before it splits at ` -> `.
- **A recreated move gets no trailer.** A move whose new path `commit --recreate` names, and whose old path the tip no longer holds, gets no trailer. Trailers are written at each commit attempt, so they match the tip of that attempt. Integration also unpairs a rename that Git's detection makes from another commit's deletion and this stage's re-added path: when no commit in base..tip moves the old path, by its trailer or by rename detection on that commit alone, the path counts as deleted, and the error names the commit that removed it. Only the renames of paths that the staged change modifies or moves are checked, so the cost grows with the stage's paths, not with the tip's renames.
- **Two moves of one path conflict.** Before the merge, a staged move whose old path a trailer since the base moved to another path gives kind `conflict` naming the old path. The stage keeps its move, so its trailer never names a path the parent lacks.
- **Refresh shares the logic.** `moveBase` calls `integrate`, so the refresh before other commands follows moves. On `path-deleted` it keeps the stage and adds the deleted paths to the "base is behind" warning.
- **Edit records follow the stage index.** `mv` rewrites the `Path` of pending records of `<old>`. Each record stores the branch tip when it was made. In `add --edits`, a record whose path is missing from the refreshed index is checked against the commits `<record tip>..<branch>`: their trailers first, then Git's rename detection on the commit that removed the path. Commit order decides, not dates. Where each path went is worked out once and applied to every record of the path. A moved path is applied at the new path. A deleted path gives `path-deleted`. `--recreate` stages the newest record's `After` as a new file and drops the older records of that path. A record from an earlier version without a tip follows the commits dated after the record, as before. Where each path went also follows the stage's own `Meta.Moves`, and a path that the stage deleted with `rm` drops its records.
- **Codex headers become operations.** `Delete File` gives a record with `After == ""`, applied like `rm` without touching the disk. `Update File` plus `Move to` gives a move record and an edit record at the new path. `add --edits` appends the move to `Meta.Moves`.
- **`rm` and `mv` write the disk last, through a journal.** The metadata save that adopts the new index also stores the pending disk operation (`Meta.PendingDisk`, a list with one entry per command: the command, its paths, and the raw bytes it expects at each path, hashed with `hash-object --no-filters` so that the check does not depend on the index or on line-ending conversion). The disk operation follows, then the journal is cleared. A rerun of the same command first finishes a matching journal entry, and only when the disk still holds the expected bytes, so it never deletes or overwrites a file that another writer created in between. An entry counts only while the stage's index still shows its change (for `rm`, each path absent; for `mv`, the old path absent and the new present); otherwise it is dropped and the command runs as new. A new `rm` or `mv` keeps the other entries. When the rename meets a target that appeared after the check, the first run restores the stage's previous index and metadata, so it changes nothing. Without a journal entry, `rm` of a path the stage's index does not hold exits with code 1. *Alternative:* disk first. Rejected: a crash would then leave the disk changed with no record of who changed it.
- **`mv` never replaces a file.** The disk rename refuses an existing target: `renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, and `MoveFileEx` without `MOVEFILE_REPLACE_EXISTING` on Windows. Where the call is not supported, it falls back to `link` then `unlink`. On a case-insensitive file system, a move between two spellings of one path (the same file by `os.SameFile`) renames in one call on macOS, where `renameatx_np` with `RENAME_EXCL` accepts it. On other systems it renames through a temporary name that the journal records, so a rerun finishes the second rename. An entry with a temporary name is never dropped before the file is renamed back or on to its target.
- **`rm` forgets its records.** `rm` drops the stage's pending records of the paths it deletes, as `mv` moves them.
- **`rm -f` and unstaged changes.** `rm` compares the disk with the stage's index entry, as `git rm` does. A difference needs `-f`, because the disk may hold another agent's unstaged lines.

## Risks / Trade-offs

- [`rm` deletes a file that holds another agent's unstaged edits] → `rm` needs `-f` when the disk differs from the stage. The other agent's records keep its edits, and it gets `path-deleted` with `--recreate`.
- [A stage committed with the previous version used `add` for a deletion] → Existing staged deletions and renames stay staged and commit as before. Only new `add` calls refuse them.
- [Trailer parsing cost on long base..tip ranges] → One `git log` per replay for the trailers, plus a few per staged path that the tip removed.
- [A move of a file that the tip also moved somewhere else] → `commit` reports kind `conflict`, before the merge.

## Migration Plan

Stages with staged deletions or renames from `add` keep them. `Meta.Moves` is optional, so old metadata reads unchanged. Rollback to the previous release ignores `Moves`: staged moves then commit as a deletion plus an addition, with no trailers.
